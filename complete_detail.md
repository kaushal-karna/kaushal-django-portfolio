# Complete Portfolio Learning Reference

This is the complete reference for the Kaushal Karn Django portfolio. It explains what was built, why the files exist, how the features work together, which commands are useful, and how a beginner can continue toward advanced Django development.

**Documentation navigation:** [Project overview](README.md) · [Command reference](command.md) · [Beginner guide](detail.md) · [Environment template](.env.example)

## 1. Finished Project Summary

This project is a personal portfolio website built with Django. It combines a server-rendered Django application with custom CSS and vanilla JavaScript.

The finished project includes:

- A futuristic responsive homepage.
- Hero, about, skills, work, journey, and contact sections.
- Project category filtering in the browser.
- Project detail pages generated from database records.
- Django admin management for projects, skills, and contact messages.
- Persistent dark and light theme selection.
- Active navigation state while scrolling.
- Responsive mobile navigation.
- Skip navigation and keyboard focus styles.
- Reduced-motion support for accessibility.
- Cursor glow, ambient background, glass panels, and reveal animations.
- Three organized profile images under `static/images/`.
- A selected profile photo in the hero card instead of the `KK` placeholder.
- A contact form with CSRF protection and server-side validation.
- Database storage for every valid contact message.
- A thank-you email to the visitor.
- A new-message notification email to the owner Gmail address.
- Plain-text and HTML versions of both email types.
- Environment-based SMTP configuration.
- WSGI and ASGI entry points for deployment.
- Beginner, command, and complete documentation.

## 4. How a Browser Request Works

A normal homepage request follows this path:

```text
Browser
  -> config/urls.py
  -> portfolio/urls.py
  -> portfolio/views.py: home()
  -> Project and Skill database queries
  -> templates/portfolio/home.html
  -> templates/portfolio/base.html
  -> static/css/style.css and static/js/app.js
  -> Rendered page in the browser
```

A contact submission follows a different path:

```text
Browser form
  -> POST /contact/
  -> ContactForm validation
  -> ContactMessage database save
  -> Visitor thank-you email
  -> Owner notification email
  -> Success or warning message
  -> Redirect back to the homepage
```

The important design decision is that the database save happens before email delivery. If SMTP is temporarily unavailable, the message is still stored and is not lost.

## 5. Django Project Configuration

### `config/settings.py`

This file controls the entire Django project. Important areas include:

- `INSTALLED_APPS`: enables Django admin, authentication, sessions, static files, and the `portfolio` app.
- `MIDDLEWARE`: enables security, sessions, CSRF protection, authentication, messages, and clickjacking protection.
- `TEMPLATES`: tells Django where templates are stored.
- `DATABASES`: configures SQLite for local development.
- `STATIC_URL`, `STATICFILES_DIRS`, and `STATIC_ROOT`: configure static assets.
- `EMAIL_*`: configure console or SMTP email delivery.
- `DEFAULT_FROM_EMAIL`: controls the sender address.
- `CONTACT_RECEIVER_EMAIL`: controls the Gmail address that receives new messages.
- `SITE_URL`: controls the link included in visitor emails.

`python-dotenv` loads `.env` before these settings read environment variables. The `.env` file is ignored by Git so secrets stay outside source control.

### `config/urls.py`

The root URL configuration provides:

- `/admin/` for Django administration.
- The empty path routed to `portfolio.urls`.

### `config/wsgi.py` and `config/asgi.py`

These expose the Django application to production servers:

- Gunicorn normally uses `config.wsgi:application`.
- Daphne normally uses `config.asgi:application`.

## 6. Database Models

### `Skill`

Stores a technology shown in the skills section.

Fields:

- `name`: skill name such as Python or Django.
- `category`: programming, web, or tools.
- `level`: numeric confidence value from `0` to `100`.
- `order`: display ordering value.

### `Project`

Stores a portfolio project.

Fields:

- `title`: visible project name.
- `slug`: URL-safe unique identifier.
- `short_description`: project-card summary.
- `description`: full case-study overview.
- `category`: Django, Web, Python, or Machine Learning.
- `tech_stack`: comma-separated technologies.
- `github_url`: optional repository link.
- `live_url`: optional deployed project link.
- `featured`: controls featured ordering.
- `order`: controls ordering among projects.

The `technologies` property turns the comma-separated field into a clean list for templates.

### `ContactMessage`

Stores submitted contact messages.

Fields:

- `name`: visitor name.
- `email`: visitor email address.
- `subject`: optional subject.
- `message`: visitor message.
- `created_at`: automatic creation timestamp.
- `is_read`: admin tracking flag.

The model is ordered newest-first so recent messages appear first in admin.

## 7. Forms, Views, and URLs

### `portfolio/forms.py`

`ContactForm` is a `ModelForm` connected to `ContactMessage`. Django validates required fields and email format before the view saves anything.

The widgets add helpful placeholders and autocomplete attributes for a better visitor experience.

### `portfolio/views.py`

The main functions are:

- `home(request)`: loads projects, skills, categories, and an empty contact form.
- `contact(request)`: accepts the POST request, validates and saves the form, then sends two emails.
- `project_detail(request, slug)`: loads one project and displays its case-study page.
- `send_contact_thank_you(contact_message)`: sends the visitor confirmation.
- `send_contact_notification(contact_message)`: sends the owner notification.

The two email functions use `EmailMultiAlternatives`, so each email contains both a text version and an HTML version.

### Public routes

| Route | View | Purpose |
| --- | --- | --- |
| `/` | `home` | Main portfolio page |
| `/contact/` | `contact` | Contact form POST endpoint |
| `/projects/<slug>/` | `project_detail` | Project case study |
| `/admin/` | Django admin | Content management |

## 9. Frontend Features

### Dark and light mode

The early script in `base.html` reads `portfolio-theme` from browser local storage. If no saved value exists, it uses the operating system preference.

`app.js` changes `data-theme` on the root HTML element and saves the new selection. CSS variables under `:root[data-theme="light"]` provide the light palette.

### Mobile navigation

The menu button toggles the `menu-open` class, updates `aria-expanded`, and changes its accessible label between open and close states. Links close the menu after selection.

### Project filtering

Each project card contains a `data-category` value. JavaScript hides cards that do not match the selected filter and updates the visible project count.

### Active navigation

An `IntersectionObserver` watches page sections and marks the matching navigation link as active while the visitor scrolls.

### Accessibility

The project includes:

- Skip-to-content link.
- `aria-label` and `aria-expanded` on controls.
- `aria-live` on the project count.
- Visible `:focus-visible` outlines.
- Image alternative text.
- Reduced-motion media query.
- Semantic sections, headings, forms, and buttons.

## 10. Profile Image Assets

The provided images are stored in:

```text
static/images/
├── profile-primary.png
├── profile-casual.jpg
└── profile-formal.jpg
```

`profile-primary.png` is currently used in the hero card. The other two are preserved for future use in an about section, project story, or dedicated profile page.

The image is rendered with `object-fit: cover` and fixed equal dimensions so it remains a clean circular avatar on desktop and mobile.

To replace the primary photo:

1. Put the new image in `static/images/`.
2. Update the path in `templates/portfolio/home.html`.
3. Run `python manage.py collectstatic --noinput` for a deployment build.
4. Reload the browser with cache disabled if the old image remains visible.

## 11. Email Delivery in Detail

### Local development

The default backend is the console backend:

```text
EMAIL_BACKEND=django.core.mail.backends.console.EmailBackend
```

This prints generated emails in the terminal. It proves the templates and recipients are correct without sending real mail.

### Real Gmail delivery

Create `.env` from `.env.example` and configure:

```text
EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend
EMAIL_HOST=smtp.gmail.com
EMAIL_PORT=587
EMAIL_HOST_USER=your-gmail-address@gmail.com
EMAIL_HOST_PASSWORD=your-gmail-app-password
EMAIL_USE_TLS=True
EMAIL_USE_SSL=False
DEFAULT_FROM_EMAIL=Kaushal Karn <your-gmail-address@gmail.com>
CONTACT_RECEIVER_EMAIL=kkarn02977@gmail.com
SITE_URL=https://your-domain.example
```

Use a Gmail App Password created after enabling two-step verification. Never put the normal Gmail password in `.env` or source code.

### Email results

For one valid submission, the application attempts:

1. One email to the visitor.
2. One email to `CONTACT_RECEIVER_EMAIL`.

Each attempt is logged if it fails. The visitor receives a specific warning when only one side succeeds. The database record remains safe in all cases.

### Email testing command

The following test uses Django's in-memory backend and never sends real mail:

```powershell
venv\Scripts\python.exe manage.py shell -c "from django.core import mail; from django.test.utils import override_settings; from portfolio.models import ContactMessage; from portfolio.views import send_contact_thank_you, send_contact_notification; override = override_settings(EMAIL_BACKEND='django.core.mail.backends.locmem.EmailBackend', CONTACT_RECEIVER_EMAIL='kkarn02977@gmail.com'); override.enable(); contact = ContactMessage(name='Test User', email='visitor@example.com', subject='Test', message='Hello'); send_contact_thank_you(contact); send_contact_notification(contact); print([email.to for email in mail.outbox]); override.disable()"
```

Expected result:

```text
[['visitor@example.com'], ['kkarn02977@gmail.com']]
```


## 17. Current Limitations

The project is strong for local development, but these areas remain before production:

- `DEBUG` must be disabled in production.
- A real secret key must be provided through environment variables.
- `ALLOWED_HOSTS` must contain the production domain.
- HTTPS redirects, secure cookies, HSTS, and trusted origins need production configuration.
- SQLite may need to be replaced with PostgreSQL or another production database.
- Automated tests should be added; currently the starter project has no test cases.
- Real SMTP credentials must be configured and verified.
- A production web server and hosting platform must be configured.

## 18. Beginner-to-Advanced Learning Roadmap

### Beginner

1. Learn Python functions, imports, lists, dictionaries, and exceptions.
2. Read `portfolio/models.py` and identify each field.
3. Run migrations and inspect the admin.
4. Read `portfolio/urls.py` and connect each URL to a view.
5. Change one template sentence and reload the browser.
6. Change one CSS variable and observe the theme.

### Intermediate

1. Add a new model field and create a migration.
2. Add a new project category and update filters.
3. Create a dedicated Django test module.
4. Test valid and invalid contact forms.
5. Add pagination to the project list.
6. Add a project image field using Pillow.
7. Add better error pages for missing project slugs.

### Advanced

1. Replace SQLite with PostgreSQL.
2. Move development and production settings into separate modules.
3. Use a secret manager for SMTP and Django secrets.
4. Add background email delivery with Celery and Redis.
5. Add rate limiting and spam protection to the contact form.
6. Add structured logging and error monitoring.
7. Add CI checks for tests, formatting, security, and static collection.
8. Deploy through Gunicorn or Daphne behind Nginx or a managed platform.
9. Add image optimization, caching, compression, and a CDN.
10. Add accessibility and performance audits to the release process.
